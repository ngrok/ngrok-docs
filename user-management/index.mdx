## Role-based access control (RBAC)

You can invite many users to the same account in the ngrok dashboard.
Each user in the account has the same account type and can start endpoints under that account.
The dashboard includes role-based access control (RBAC) as a way to limit what users have access to in the account.
You can manage these roles and add more users to your account on the [team members page](https://dashboard.ngrok.com/team-members) of the dashboard.
This is only available for paid plans.

## Single sign-on (SSO)

If you're a Pay-as-you-go customer, you can enable single sign-on (SSO) for your users logging into the ngrok Dashboard and add the SSO & RBAC add-on.
Account admins can find the configuration options under [**Settings > Account**](https://dashboard.ngrok.com/settings) once they log into the dashboard.

ngrok supports most [SAML v2 compliant identity providers](https://en.wikipedia.org/wiki/SAML-based_products_and_services), including [Okta](https://help.okta.com/oie/en-us/Content/Topics/Apps/apps-about-saml.htm) and [Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/architecture/auth-saml).
To get started with the configuration, click **+ New Identity Provider** and follow the instructions in the dashboard.
ngrok supports multiple identity providers as well.
If you use multiple identity providers, ngrok prompts the user to choose one when they log in with SSO from the ngrok login page.

After you configure the correct information with your identity provider, you can enable or disable logging in directly from your provider.
This is helpful if your users want to jump directly to their ngrok account from a centralized location once they've logged into their identity provider.

You can also choose how new users are added to the account.
If you'd like ngrok to automatically provision new users in the account when they log in, you can enable Just in Time (JiT) provisioning.
This adds users to your account when they use the link from the identity provider.
If you'd rather only allow invited users to join, you can select **Invite Only**, which requires new users to be invited through the teams page before they're added to the account.

ngrok supports two enforcement options once you've configured your identity provider.
When you're testing and verifying that the integration works, it's helpful to enable **Mixed Mode**, which still allows you and the users of your account to log into the account using your previous credentials.
Once you're satisfied that everything works correctly, you can enable **SSO Enforced** mode, which requires all users in the account to authenticate through one of the configured identity providers.

## Service Users

### What is a Service User?

A Service User is a service account that owns a set of credentials—authtokens, API keys, and SSH keys—independently of a person.
You can see and manage your Service Users in the [ngrok Dashboard](https://dashboard.ngrok.com/service-users).

Service Users are similar to [Users](/iam/users/), but they're intended for automated systems that programmatically interact with your ngrok accounts, either by starting ngrok Agents or making requests to the API.

Other platforms you may interact with sometimes call this concept a _Service Account_.

Service Users differ from Users in a few important ways:

- Service Users can't log into the Dashboard.
- Service Users can't be a member of more than one Account.
- Service Users don't count against any seat counts or limits.

Service Users facts and limitations:

- Service Users may be attached to services that consume ngrok platform resources and can trigger overages.
  These areas include metrics like bandwidth, total sessions and endpoints, authtokens, API tokens, and more.
- Service Users have limited functionality:
  - Service Users can't log into the ngrok Dashboard.
  - Service Users can't be assigned or shared among multiple accounts.
- Benefits of Service Users:
  - You can connect credentials that are unique to a specific service or function to a Service User instead of to a person.
    A standard user may leave the account or want to rotate their credentials, and these actions shouldn't impact production services running in ngrok.
  - ngrok attributes logs to a Service User, which helps you better understand what a specific production service in ngrok is doing, even when there are multiple production services in the same account.
  - You can deactivate a Service User to temporarily suspend all credentials associated with it—making ngrok more secure.
  - You can delete a Service User to immediately revoke and delete all credentials associated with it—making ngrok more secure.

### How to create a Service User

You can create a Service User in the dashboard or programmatically through the ngrok API.

In the [ngrok Dashboard](https://dashboard.ngrok.com/service-users), go to **Users** and then **Service Users** to create a new Service User.

Using the API, you can POST to the [`/service_users` endpoint](/api-reference/serviceusers/create).

### When to use a Service User

A Service User is best suited to own the credentials of shipped products, devices, and integrations in production.
The ideal flow is a credential you can associate with a specific task, keep active, and rotate on a predictable schedule because it's unique to that integration, service, or function.

Service Users are available on all ngrok free and paid plans.

### When not to use a Service User

A Service User is very useful, but it's not a good substitute for a standard ngrok User.
When developers build with ngrok, they may need to rotate credentials after adding them to a build environment or accidentally committing them to a repository.
The developer needs to use the ngrok dashboard to see endpoint status, make configuration changes, and manage their own credentials, which a Service User can't do.

### Deleting a Service User

When you delete a Service User, ngrok immediately revokes and deletes all credentials owned by the user.
You can't restore deleted credentials.
If this happens, create new credentials under a new or existing Service User.

### Inactive Service Users

When you mark a Service User as inactive, it remains in the account, but its credentials no longer work.
This is a good way to test what might break if you completely remove the Service User.

### Moving former employee credentials (API keys, authtokens, SSH keys) to a Service User

Credentials are assigned an owner when they're created, and you can't change the owner.
Go to the [ngrok Dashboard](https://dashboard.ngrok.com/service-users) to create a new Service User.
