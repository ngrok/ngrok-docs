When you deploy into highly restricted, secure networks, such as banks, hospitals, factories, or government agencies, the customer's security team reviews every piece of software before it runs.
They check who published the binary, who signed the installer, and where it connects to.
A third-party agent with someone else's name on it can slow that review down or stop it entirely.

Fleet Connector is a reference implementation, built on the [ngrok Go SDK](/agent-sdks), that you rename and sign as your own.
Your customers see your software, from your publisher name to the service on their machines, while ngrok handles the connectivity underneath.
You control:

- **The binary and service name**, so the process on the customer's machine carries your brand.
- **The signature**, so Windows shows your company as the publisher instead of ngrok.
- **The installer**, so you can ship an MSI or Linux package that fits your customers' deployment tools.
- **The update channel**, so new builds come from your own server, signed by you.

If you don't need your own brand or signature, [run the standard ngrok agent as a background service](/gateway/site-to-site-connectivity/background-service) instead.
It's already signed by ngrok.

## What you'll need

- An ngrok account.
  If you don't have one, [sign up](https://dashboard.ngrok.com/signup).
- An [authtoken](https://dashboard.ngrok.com/authtokens) for each install, or an [API key](https://dashboard.ngrok.com/api-keys) to create one per install automatically.
- [Go](https://go.dev/dl/) on your build machine.
- For Windows, a code-signing certificate from a trusted certificate authority (CA).

<Steps titleSize="h2">
  <Step title="Fork the repository">
    [Fork the Fleet Connector repository](https://github.com/ngrok-adhoc/fleet-connector/fork) before you change anything.
    Your service name, branding, and signing certificate live in your fork, not in the original.
  </Step>

  <Step title="Build your release">
    Build once on your own build machine, not on every install.
    The output is the installer you distribute to your customers.

    <Tabs>
      <Tab title="Windows">
        Build the binary and an MSI installer with [WiX v5](https://wixtoolset.org/):

        ```powershell
        git clone https://github.com/<your-org>/fleet-connector.git
        cd fleet-connector
        go build -o fleetconnect.exe .\cmd\fleetconnect

        dotnet tool install --global wix --version "5.*"
        wix extension add WixToolset.Util.wixext/5.0.2
        wix build installer\product.wxs `
          -ext WixToolset.Util.wixext/5.0.2 -arch x64 `
          -d FleetConnectExeSource=fleetconnect.exe `
          -out FleetConnector.msi
        ```

        Then sign the MSI.
        Fleet Connector is built from source, so it doesn't carry ngrok's signature.
        If you skip this step, the MSI is unsigned: Windows SmartScreen warns about an unknown publisher, antivirus tools may flag it, and you can't turn on remote updates.

        ```powershell
        $cert = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
          Where-Object Subject -eq "CN=Your Company"

        Set-AuthenticodeSignature -FilePath FleetConnector.msi `
          -Certificate $cert -HashAlgorithm SHA256

        (Get-AuthenticodeSignature FleetConnector.msi).SignerCertificate.Thumbprint
        ```

        Save the thumbprint from the last command.
        You need it to turn on remote updates.

        <Tip>
        To test without a CA-issued certificate, create a self-signed one with `New-SelfSignedCertificate -Type CodeSigningCert -CertStoreLocation Cert:\CurrentUser\My -Subject "CN=Your Company"`.
        </Tip>
      </Tab>
      <Tab title="Linux">
        Build the binary and a `.deb` package with [nFPM](https://nfpm.goreleaser.com/):

        ```bash
        git clone https://github.com/<your-org>/fleet-connector.git
        cd fleet-connector
        GOOS=linux GOARCH=amd64 go build -o fleetconnect ./cmd/fleetconnect

        go install github.com/goreleaser/nfpm/v2/cmd/nfpm@latest
        nfpm package --config installer/linux/nfpm.yaml \
          --packager deb --target dist/
        ```

        To build an `.rpm` package instead, use `--packager rpm`.
      </Tab>
    </Tabs>
  </Step>

  <Step title="Distribute and install">
    Publish the signed installer to an HTTPS location you control, such as your own download server or object storage bucket, and share its SHA-256 checksum.
    On Windows, use the same location as your `update_source_url` so first installs and remote updates come from one place.

    Your customer's IT team, or your remote monitoring and management (RMM) tool, then delivers the installer to each target machine with the tools they already use, such as Microsoft Intune, Configuration Manager, Ansible, or an internal package repository.
    For silent installs, have the same script write `config.yaml` with [`gen-config`](#gen-config) before it runs the installer, so the service starts with the right config.

    <Note>
    Highly restricted networks often can't download from the internet at all.
    In that case, hand the installer and its checksum to the customer's IT team, and they import it into their internal software distribution system.
    </Note>

    The installer runs Fleet Connector as a background service that starts on boot:

    <Tabs>
      <Tab title="Windows">
        Run in PowerShell as Administrator:

        ```powershell
        msiexec /i FleetConnector.msi /quiet
        ```
      </Tab>
      <Tab title="Linux">
        ```bash
        sudo dpkg -i fleetconnect_*.deb
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Configure the agent">
    Fleet Connector reads its settings from a `config.yaml` file:

    - Windows: `C:\ProgramData\FleetConnector\config.yaml`
    - Linux: `/etc/fleetconnect/config.yaml`

    You can create this file in three ways, depending on who installs it and when:

    - **`gen-config`**: Write the file before the service first starts.
      Use this for silent, scripted installs, such as an RMM tool pushing to many machines at once.
    - **Setup wizard**: If no `config.yaml` exists when the service starts, it opens a web form on `127.0.0.1`.
      The form walks a person through setup once, then shuts down after it writes a valid config.
    - **Hand-edit**: Edit `config.yaml` directly, or run `fleetconnect edit-config` to edit it in `$EDITOR` with validation before it saves.

    ### gen-config

    This command creates a private endpoint at `https://store-042.ngrok.direct` that forwards to `localhost:8080`, and turns on remote updates.
    Only your own ngrok account can reach the endpoint.

    ```bash
    ./fleetconnect gen-config \
      --description "store-042" \
      --url https://store-042.ngrok.direct \
      --binding internal \
      --upstream localhost:8080 \
      --authtoken "<your authtoken>" \
      --update-source-url "https://updates.example.com/latest/fleetconnect.msi" \
      --update-signer-thumbprint "AABBCCDDEEFF00112233445566778899AABBCCDD"
    ```

    It writes the following `config.yaml`:

    ```yaml
    schema_version: 1
    description: store-042
    credential:
        provider: static
        params:
            authtoken: <your authtoken>
    endpoints:
        - url: https://store-042.ngrok.direct
          upstream:
            url: localhost:8080
          bindings:
            - internal
    update_source_url: https://updates.example.com/latest/fleetconnect.msi
    update_signer_thumbprint: AABBCCDDEEFF00112233445566778899AABBCCDD
    ```

    By default, `gen-config` writes to `config.yaml` in the current directory.
    Use `--path` to write it to the service's config location instead.

    | Flag | Description |
    | --- | --- |
    | `--description` | Human-readable description. Required. |
    | `--url` | Endpoint URL for a single endpoint, such as `https://store-042.ngrok.direct`. |
    | `--upstream` | Local address a single endpoint forwards to, such as `localhost:8080`. |
    | `--binding` | Binding for a single endpoint: `public` (default), `internal`, or `kubernetes`. |
    | `--endpoint` | One endpoint, as `"name=...,upstream.url=...,url=...,bindings=..."`. Repeat for multiple endpoints. Can't be combined with `--url`, `--upstream`, or `--binding`. |
    | `--authtoken` | A literal value, `env:VAR`, or `file:PATH`. |
    | `--path` | Where to write the config. Defaults to `config.yaml` in the current directory. |
    | `--connect-url` | Your [custom connect URL](/gateway/site-to-site-connectivity/custom-connect-url). |
    | `--connect-ca-cert-file` | PEM CA bundle to trust for `--connect-url`. |
    | `--proxy-url` | Outbound HTTP or SOCKS proxy for the agent's own connection. |
    | `--heartbeat-interval` | Connection heartbeat interval, such as `30s`. |
    | `--heartbeat-tolerance` | How long to tolerate a missed heartbeat, such as `1m`. |
    | `--update-source-url` | Windows only. Leave it blank to turn off remote updates. |
    | `--update-signer-thumbprint` | Required when you set `--update-source-url`. |

    ### config.yaml reference

    ```yaml
    schema_version               required, must be 1
    description                  human-readable label (optional)
    metadata                     session metadata visible in the dashboard and API (optional)
    credential:
      provider                   required, "static" is the only built-in provider
      params:
        authtoken                the authtoken the agent connects with
    endpoints:                   one entry per endpoint (optional)
      - name                     friendly name (optional)
        url                      endpoint URL; blank = https, or tcp://, tls://
        upstream:
          url                    required, local address to forward to
          protocol               "http1" (default) or "http2"
          proxy_protocol         "1", "2", or empty
          tls_verify             verify the upstream's TLS certificate (default: false)
          tls_verify_cas         PEM CA bundle path; empty = system CA pool
        bindings                 for example ["public"] or ["internal"] (optional)
        metadata                 per-endpoint metadata (optional)
        description              per-endpoint description (optional)
        traffic_policy           inline Traffic Policy, YAML or JSON string (optional)
        agent_tls_termination:   (optional)
          server_certificate     PEM certificate
          server_private_key     PEM private key
          mutual_tls_certificate_authorities   PEM CA bundle (optional)
        pooling_enabled          bool (optional)
    connect_url                  custom connect URL (optional)
    connect_ca_cert_file         PEM CA bundle to trust for connect_url (optional)
    proxy_url                    outbound HTTP or SOCKS proxy for the agent's own connection (optional)
    heartbeat_interval           for example "30s" (optional)
    heartbeat_tolerance          for example "1m" (optional)
    log_level                    debug, info (default), warn, or error
    update_source_url            Windows only; blank turns off remote updates
    update_signer_thumbprint     required when update_source_url is set
    ```
  </Step>

  <Step title="Operate the service">
    Check, stop, and start the service, and follow its logs:

    <Tabs>
      <Tab title="Windows">
        ```powershell
        sc.exe query FleetConnector
        sc.exe stop FleetConnector
        sc.exe start FleetConnector

        Get-Content `
          C:\ProgramData\FleetConnector\logs\fleetconnect.log `
          -Tail 20 -Wait
        ```
      </Tab>
      <Tab title="Linux">
        ```bash
        systemctl status fleetconnect
        systemctl stop fleetconnect
        systemctl start fleetconnect

        journalctl -u fleetconnect -f
        ```
      </Tab>
    </Tabs>
  </Step>
</Steps>

## Remote updates

On Windows, you can push a new build to your fleet without touching each machine.
To turn on remote updates, set both of these fields in `config.yaml`:

- `update_source_url`: Where the agent downloads a new signed MSI from.
- `update_signer_thumbprint`: The thumbprint of the certificate that must have signed it.

When you send an update from the ngrok dashboard or API, the agent receives it over its existing connection.
It downloads the MSI and checks the signature against the pinned thumbprint before installing it.

Remote updates aren't available on Linux, because the update process installs an MSI.
On Linux, roll out new `.deb` or `.rpm` packages with your existing package management or RMM tools.
