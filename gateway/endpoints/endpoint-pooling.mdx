Endpoint pooling makes load balancing dead simple.
Load balancing helps you scale traffic across multiple replicas of your app to increase capacity, tolerate failures, and geo-distribute load.
When you create two endpoints with the same URL (and binding), those endpoints automatically form a "pool" and share incoming traffic.

Endpoint pooling is vastly more flexible than comparable load balancing systems:

- Endpoints join and leave pools automatically as they're created and destroyed.
  There's no need to register your upstreams ahead of time.
- You can pool endpoints with different Traffic Policies.
  This means that not only can you blue-green and canary deploy your own apps, you can also do that with the Traffic Policies themselves.
  This helps you dramatically mitigate the risk of gateway changes that so often cause site-wide outages.

## When to use endpoint pooling

Endpoint pooling is a good choice when you want to:

- Load balance among multiple replicas of the same application, even running in different cloud providers, on-prem, and so on
- Switch from Agent Endpoints to Cloud Endpoints with no downtime (or vice-versa)
- Implement blue-green deployments to reduce risk and rollback times
- Deploy canary versions of your application
- A/B test different versions of your apps with blue-green deployments
- Gradually roll out changes to an endpoint's Traffic Policy

## Quickstart

### Agent Endpoints

Create two endpoints with the same URL forwarding to two different ports.
ngrok automatically pools them together.

```
ngrok http 8080 --url https://your-domain.ngrok.app --pooling-enabled=true
```

```
ngrok http 9090 --url https://your-domain.ngrok.app --pooling-enabled=true
```

When you make requests to the endpoints' URL, you'll see responses balanced among each endpoint in the pool.

```
curl https://your-domain.ngrok.app
<Response from 8080>

curl https://your-domain.ngrok.app
<Response from 9090>
```

### Cloud Endpoints

Create two endpoints with the same URL and two different Traffic Policies.
ngrok automatically pools them together.

First, create two Traffic Policy files, `policy-a.yml` and `policy-b.yml`.

```yaml title="policy-a.yml" mode=traffic-policy
on_http_request:
  - actions:
      - type: custom-response
        config:
          status_code: 200
          body: Policy A
```

```yaml title="policy-b.yml" mode=traffic-policy
on_http_request:
  - actions:
      - type: custom-response
        config:
          status_code: 200
          body: Policy B
```

Then create two Cloud Endpoints, one with each policy:

```bash title="Command line"
ngrok api endpoints create \
    --url https://your-domain.ngrok.app \
    --traffic-policy "$(cat policy-a.yml)" \
    --pooling-enabled=true

ngrok api endpoints create \
    --url https://your-domain.ngrok.app \
    --traffic-policy "$(cat policy-b.yml)" \
    --pooling-enabled=true
```

When you make requests to the endpoints' URL, you'll see responses balanced among each endpoint in the pool.

```bash title="Command line"
curl https://your-domain.ngrok.app
<Response from 8080>

curl https://your-domain.ngrok.app
<Response from 9090>
```

## Lifecycle

ngrok automatically creates an endpoint pool whenever you create two endpoints with:

- The same URL
- The same binding
- Pooling enabled

When only a single endpoint remains in a pool, it's no longer pooled with others, but the endpoint remains poolable and can accept additional entries.

## Enabling pooling

Endpoint pooling is disabled by default.
You enable endpoint pooling on a per-endpoint basis.
You must enable pooling on each endpoint you want to pool by setting `pooling_enabled` to `true`.

## Drain and close a pool

A pool exists only while two or more endpoints share its URL and binding, so you drain a pool by stopping endpoints in it.
When you stop an endpoint, ngrok stops routing traffic to it, and the remaining endpoints in the pool receive all of the traffic.

To list the endpoints in a pool, filter your endpoints by URL:

```bash
ngrok api endpoints list --filter 'obj.url == "https://your-domain.ngrok.app"'
```

### Stop an endpoint in a pool

- **Agent Endpoint:** Stop the ngrok agent, or remove the endpoint from your agent configuration file or SDK code.
- **Cloud Endpoint:** Delete the endpoint with `ngrok api endpoints delete <endpoint_id>`.

To take the URL offline entirely, stop every endpoint in the pool.
If the pool has only one endpoint left, stopping that endpoint takes the URL offline.

### Turn a pooled endpoint into a non-pooled endpoint

You can't turn off pooling while other endpoints share the URL, so first stop every other endpoint in the pool.

- **Cloud Endpoint:** After it's the only endpoint on its URL, update it to turn pooling off.
  The URL stays online throughout.

  ```bash
  ngrok api endpoints update <endpoint_id> --pooling-enabled=false
  ```

  If another endpoint still shares the URL, the update fails with a `400` error.
- **Agent Endpoint:** You can't change pooling on a running Agent Endpoint.
  Stop every Agent Endpoint in the pool, then start a new endpoint without `--pooling-enabled` (or with `pooling_enabled: false` in your configuration file).
  The URL is offline between stopping the last pooled endpoint and starting the new one.

  ```bash
  ngrok http 8080 --url https://your-domain.ngrok.app
  ```

## Pool size

There's no limit on the number of endpoints that can be in a pool.

## Conflicts

If you create a second endpoint with the same URL and binding as an existing endpoint, both the new endpoint and existing endpoint must have [pooling enabled](#enabling-pooling).
If they don't, ngrok returns a conflict error when you attempt to start the second endpoint.

The URLs of all endpoints in a pool must share the same protocol.
For example, you can't pool the endpoints `https://foo.internal:1234` and `tcp://foo.internal:1234` together because they have a different protocol.

For Agent Endpoints, conflicts can only occur when the endpoint starts, because you can't change the URL or pooling setting of a running Agent Endpoint.
For Cloud Endpoints, conflicts can also occur when you update the URL or pooling setting.

## Load balancing

Traffic to pooled URLs is load balanced among the endpoints in the pool.
ngrok applies load balancing in two places:

- When pooled public and Kubernetes endpoints load balance traffic received from external clients.
- When pooled internal endpoints receive traffic that's forwarded to them via the `forward-internal` Traffic Policy action.

### Granularity

ngrok intelligently chooses the load balancing layer automatically for you.

Traffic to TCP and TLS endpoints is balanced on a per-connection basis (layer 4).

Traffic to HTTP and HTTPS endpoints is balanced on a per-request basis (layer 7).
If multiple endpoints in a pool have different `on_tcp_connect` phases in their Traffic Policy, ngrok instead load balances on a per-connection basis (layer 4).

### Heterogeneous endpoints

Endpoints in a pool can have different Traffic Policies.
This lets you run old and new Traffic Policies side-by-side during a transition.
It also enables you to roll out new Traffic Policy changes without risking an all-or-nothing deployment.

When traffic is balanced among endpoints with different Traffic Policies, ngrok first chooses an endpoint to balance to and then executes the Traffic Policy of the chosen endpoint.

### Default strategy

ngrok's default balancing strategy attempts to strike a balance between performance and fairness:

- First, it identifies all endpoints in the pool that are in the point of presence closest to where a connection is received.
- Then, it balances connections in a random distribution among those endpoints.

For the purposes of the first step, ngrok considers [Cloud Endpoints](/gateway/endpoints/cloud-endpoints) to be online in all points of presence.

For example, if an endpoint pool consists of the following endpoints:

- Endpoint A: Agent Endpoint connected to `eu`
- Endpoint B: Agent Endpoint connected to `eu`
- Endpoint C: Agent Endpoint connected to `us`
- Endpoint D: Cloud Endpoint

Then:

- A connection received in `eu` is balanced among endpoints A, B, and D
- A connection received in `us` is balanced among endpoints C and D
- A connection received in `jp` is balanced to endpoint D

### Retries

When a connection or request is balanced to an endpoint in a pool, if that connection or request fails, ngrok doesn't retry it by sending it to another endpoint in the pool.

## Wildcard endpoints

Wildcard endpoints don't pool with non-wildcard URLs.
For example, if you have two endpoints online, `https://foo.example.com` and `https://*.example.com`, they don't pool together, and traffic to `https://foo.example.com` isn't load balanced.
See the documentation for [wildcard endpoints](/gateway/endpoints/cloud-endpoints/http#wildcard-endpoints) to understand the rules for matching and precedence.

## Protocol, binding, and type

- Endpoint pooling supports all endpoint protocols
- Endpoint pooling supports all endpoint bindings
- Endpoint pooling supports all endpoint types (and you can mix types in an endpoint pool)

## API

Because ngrok creates endpoint pools on demand when two endpoints share the same URL and binding, there's no API resource for endpoint pools.
Instead, each [Endpoint API Resource](/api-reference/endpoints/list) has a read-only `pools` field that lists the other endpoints in the same pool as the requested endpoint.
