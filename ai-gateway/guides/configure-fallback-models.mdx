Use fallback models when you want the AI Gateway to try another model if the primary request fails.

Fallback is useful when you want better availability across providers, or when you want to try a private model first and use a hosted model as a backup.

## Add fallback models

Set the primary model with `model`.
Set fallback models with `models`.

```json
{
  "model": "gpt-4o",
  "models": ["gpt-4o-mini", "anthropic:claude-sonnet-4-6"],
  "messages": [{"role": "user", "content": "Hello"}]
}
```

The gateway tries `gpt-4o` first.
If that request fails with a rate limit, an auth error, a server error, or a timeout, it tries each entry in `models` in order until one succeeds.
Other 4xx errors, such as an invalid request, return right away.
See [what triggers failover](/ai-gateway/guides/error-handling).

## Choose the provider for each fallback

Fallback models can use model IDs or `provider:model`.

```json
{
  "model": "openai:gpt-4o",
  "models": [
    "openai:gpt-4o-mini",
    "anthropic:claude-sonnet-4-6"
  ],
  "messages": [{"role": "user", "content": "Hello"}]
}
```

Use provider-qualified model names when you want to control exactly which provider each fallback uses.

## Fall back from a private model to a hosted model

Fallback works with [custom providers](/ai-gateway/concepts/custom-providers), too.

```json
{
  "model": "my-ollama:llama3.2",
  "models": ["openai:gpt-4o-mini"],
  "messages": [{"role": "user", "content": "Hello"}]
}
```

In this example, the gateway tries your `my-ollama` provider first.
If that request fails, it falls back to OpenAI.

## Choose fallback models carefully

Pick fallback models that can handle the same kind of request as the primary model.
Check each model for:

- Input modality.
- Tool calling support.
- Output size.
- Context window.
- Latency expectations.
- Provider credentials.

Use the [model catalog](/ai-gateway/reference/model-catalog) to compare built-in model capabilities.

## Access restrictions still apply

The [access key configuration](/ai-gateway/guides/access-key-configurations) assigned to the access key must allow your fallback models.

If a fallback model isn't allowed, the gateway skips it and names it in the `Ngrok-AIG-Rejected-Models` response header.
The request still runs with the models that are allowed.
It fails only when none of the models you listed are allowed.

## Save a fallback list as a virtual model

To keep the list out of your code, save it as a [virtual model](/ai-gateway/guides/virtual-models) and send its name as `model`.
You can then change the models and their order from the gateway, without changing your requests.
This also works for a client that can't send a `models` array.
A virtual model follows the same failover rules as a `models` list.
